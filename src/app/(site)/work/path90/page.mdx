A design shows the happy path. Building it meant deciding what happens around the edges:

- **Offline states.** When the connection drops, a banner says the app is showing saved data and how many changes are waiting. Completing a task offline says "Saved, will sync when back online" instead of pretending it reached the server.

- **Touch targets.** Navigation and primary controls are at least 44px.
- **Bottom navigation.** In July, Appointments replaced Profile in the mobile navigation.

#### Physical data model

The domain model became tables almost one to one. The assignment table carries the copied settings, the completion state, and the reminder flags that make scheduled jobs safe to rerun:

```sql
create table public.user_tasks (
  id               uuid    primary key default gen_random_uuid(),
  task_id          uuid    not null references public.tasks(id) on delete cascade,
  user_id          uuid    not null references public.users(id) on delete cascade,
  appointment_id   uuid    references public.appointments(id) on delete set null,
  due_date         date    not null,
  priority         public.task_priority  not null default 'medium',
  frequency        public.task_frequency not null default 'once',
  is_mandatory     boolean not null default false,
  time_estimate    text,
  is_completed     boolean not null default false,
  completed_at     timestamptz,
  completed_by_admin boolean not null default false,
  due_reminder_sent    boolean not null default false,
  missed_reminder_sent boolean not null default false,
  unique (task_id, user_id, due_date)
);
```

And the status diagram above is this one expression, evaluated on every read:

```sql
select case
  when (select last_active_at from u) is null
    or (select last_active_at from u) < now() - interval '7 days'
    then 'inactive'
  when (select flag from missed)
    or (
      (select total from recent) > 0
      and (select done from recent)::numeric / (select total from recent) < 0.5
    )
    then 'at_risk'
  else 'on_track'
end;
```

#### Deep dive: a queue that survives closing the app

React Query can pause a mutation while the phone is offline and persist it with the rest of the cache. The catch is that a function cannot be serialized. A mutation restored from IndexedDB after the app was closed comes back with its variables but without the code to run. So the two offline mutations are registered as defaults on the query client under a key, and every screen that completes a task uses the key rather than its own function:

```ts
qc.setMutationDefaults(MUTATION_KEYS.completeUserTask, {
  mutationFn: (userTaskId: string) => completeUserTask(userTaskId),
  onMutate: async (userTaskId: string) => {
    await qc.cancelQueries({ queryKey: ['tasks'] })
    const previous = qc.getQueriesData({ queryKey: ['tasks'] })
    // Trimmed: mark the task complete in every cached list and in the
    // detail view, then show "done" online or "saved, will sync" offline.
    return { previous }
  },
  onError: (_err, _vars, context) => {
    // Trimmed: restore every cached list from `previous`.
  },
  onSettled: () => {
    qc.invalidateQueries({ queryKey: ['tasks'] })
  },
})
```

On startup the provider restores the cache from IndexedDB and then calls `resumePausedMutations()`, so a task ticked on the bus syncs the next time the app opens with a signal. The persisted cache carries a version key that I bump whenever the shape of a task changes, so an old cache never feeds new code. I bumped it once, when assignments started carrying their own settings (D4).

#### Testing and delivery

CI runs lint and a TypeScript check on every pull request to main, dev, and phase branches. Vercel only builds those branches, and the pull request checklist asks for a check at 375px and an install test on iOS Safari and Android Chrome. There are no automated tests. The type checker and the database policies carry the weight, and the policies are exactly the code that should have a test suite next.

In July I moved the backend from a Supabase project in the EU to one in the US, keeping the EU project as a rollback. A schema dump leaves things behind, so I recreated the Vault secrets by hand and restored the trigger on `auth.users` that creates a participant's profile at sign-up.

### Retrospective

Working from someone else's design moved my product work to the edges the design did not draw: what offline looks like, what an iPhone user sees instead of an install button, what a badge means exactly. Those edges are where a participant decides whether to trust the app.

On the engineering side, deciding what not to make offline kept the project on schedule. Two queued writes and a cached read path covered the daily loop. A full sync engine would have taken the whole timeline.
