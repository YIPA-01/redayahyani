## The product and my part

<Callout label="The client’s work and mine">
  The product, its business rules, and the app’s design were the client’s,
  and the Flutter app was built by another team. My part was everything the
  app talks to: the data, the rules that guard it, the functions that compute
  every number, the integrations, and the portal the client uses to run it.
</Callout>

The app is built around one number, equity: what the car is worth minus what is still owed. Around it sit a readiness badge, a garage of the owner's cars, a preference quiz on ten dimensions that ranks twelve package families, a catalog to browse and save from, a payment comparison against any catalog car, and the assistant.

{/* TODO: one figure of the real app screens (dashboard with the badge, and
    the comparison screen). Nothing in the backend repo shows them. */}

A spec describes what the numbers are. Building it meant deciding what happens when a number cannot be honest:

- **A car with nothing to value from.** An owner who has paid off their car, and whose model is not in the catalog, gives the engine nothing to start from. The snapshot stores `null` with `determinable: false`, not $0, and the app shows "We can't estimate your car's value yet" and hides the badge.
- **A trade-in worth more than the next car.** The comparison used to show a $0 payment. It now says the trade-in covers the car and shows what is left over.
- **A wrong spreadsheet.** An upload that would remove more than a quarter of the live catalog stops and asks for confirmation, so a truncated file cannot silently wipe models.
- **The launch offer.** The first 500 registrations get Premium free. A server-side counter numbers every real signup, so the offer cannot be claimed twice or from the app.

#### Physical data model

The domain model became seventeen collections. What changed on the way: versions became append-only documents grouped by `car_id`, a relation became a pinned document id (a favorite is `{uid}__{catalog_car_id}`, so the rules can check ownership from the path), and trims became a `configurations` subcollection with permanent random IDs (R8). The display name is stored as a lookup field and is never the key, because manufacturers reuse names. Six collections deny every client read and write: push tokens, Stripe customers, the sweep's memory, runtime config, the price cache, and the signup counter.

The rule that made `chat_messages` safe (D2) is short:

```js
match /chat_messages/{docId} {
  allow read: if isOwner(resource.data.uid);
  allow write: if false;
}
```

#### Deep dive: the equity engine

The engine answers one question: is the car worth more than what is owed, and is it time to trade?

```
equity = trade_value − payoff_balance
badge  = ready | almost_ready | not_yet
```

The second line is the easy part. The hard part is the first term, because there was no honest source for it. Edmunds' public API is shut down, the trim-level sources that do exist are paid, NHTSA's data has no prices, and the one open dataset I found was synthetic. An LLM would have invented both the number and its source, which is not acceptable for a financial figure. So I split the problem in two. Everything that consumes a trade value (equity, the badge, the snapshot, the comparison, the alerts) is final code. Only the number itself is provisional, behind one function with a fixed signature:

```ts
export function computeTradeValue(
  profile: CarProfile,
  catalogMsrp?: number | null,
  nowYear: number = new Date().getFullYear()
): TradeValueResult {
  // Base: the catalog MSRP, or down payment + monthly payment × term.
  // Neither: return trade_value null, determinable false. Never $0.
  const age = Math.max(0, nowYear - profile.year)
  const ageFactor = Math.pow(1 - ANNUAL_DEPRECIATION, age)
  const mileageFactor = computeMileageFactor(profile, age)
  const tradeValue = Math.max(
    0,
    base * ageFactor * conditionMultiplier * mileageFactor
  )
  return {
    trade_value: round2(tradeValue),
    determinable: true,
    depreciation_curve_used: curve, // which base, versioned
    condition_multiplier: conditionMultiplier,
    mileage_factor: round2(mileageFactor),
    disclaimer: DISCLOSURES.estimatedValue,
  }
}
```

Mileage is a multiplier, not a dollar amount: the odometer is judged against 12,000 miles a year for the car's age and clamped between 0.6 and 1.05, so a luxury car and an economy car lose the same share, not the same dollars (R2). The disclaimer is set here, inside the result, so no consumer can show the number without it (R1). Payoff and months left are entered once and then aged on every read from the date the terms were entered, so a badge climbs on its own as a loan runs down, with no monthly job.

On 27 July the client pushed back on the rules: no fixed depreciation percentages, no flat mileage deduction, five condition levels, credit-based APR, ZIP-based tax, a value range with a confidence level. Before writing any code I mapped every point against what the engine actually did, smallest gap first. Mileage already matched. The flat curve met the client's own bar for version 1 ("an internal estimation model with a clear disclaimer"). The real work was the payment side, which had a hardcoded 7.5% rate and no tax at all.

A credit profile picks the rate (5.5% Excellent, 7% Good, 9.5% Average, 13.5% Building), a custom rate overrides it, then the rate saved on the account, and only then the old default (R4). Sales tax comes from a 50-state table the client supplied, including the states that tax the full price with no trade-in credit and Michigan's partial credit (R5). Four days later a review found the app saved a ZIP code but never a state, so the tax was reaching nobody. The backend now derives the state from the ZIP, and an unknown state adds no tax and says so, rather than guessing a national average.

The numbers that justify the approach: 353 unit tests run in under a second, because every rule above is a pure function with no Firestore and no clock. That is what made it cheap to rework the payment rules after the July feedback without breaking the contract with the app team.

What the engine still does not do is on this page as misses: one trade value, not a range with a confidence level (R7), the old condition labels (R3), and no cash or combined down payment (R6).

#### Alerts that mean something

The other half of R10 runs while nobody has the app open. Once a day a scheduled sweep recomputes every car and compares it with what it knew yesterday. The evaluator is pure, and built on two rules: an alert fires on a change, never on a condition that is still true, and an alert held back by a limit is kept for the next day rather than lost. Three kinds exist: the badge moved up, a payment milestone was reached, or equity moved by at least $500 and at least 5%. Both, because 5% of $200 is noise and $500 on a $250,000 car is noise. A car's first sweep is silent, so launch day cannot send everyone a burst of alerts, and no owner gets more than one alert per car per day or three a week.

#### Testing and delivery

Every rule that decides a number or an alert is a pure module with unit tests: 353 of them, all passing as of this writing. On top of that, an emulator suite runs every function against real Auth and Firestore emulators, three integration scripts cover the catalog upload and the Stripe webhook, and 87 rules tests pin who can read and write what. GitHub Actions runs the build, lint, and unit tests, then the emulator suites, on every push to main and every pull request. Smoke scripts check the live project after a deploy, including one that validates a push without delivering it. The admin portal deploys to Firebase App Hosting.

### Retrospective

Working on the backend only, my product work happened in the numbers. Every rule the client sent back was about trust: a range instead of a figure, a disclaimer on everything, no promise of a payment. The calls I am happiest with are the small honest ones, like showing "we can't estimate this yet" instead of $0.

On the engineering side, splitting the provisional number from the final code around it is what let the payment rules change late in the build without breaking the app. The miss is that I did that for the trade value but not for the shape of the answer: a range with a confidence level is a contract change for the app team, and it is still waiting.
