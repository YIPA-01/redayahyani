## Understanding the user

I talked to students looking for rooms and put early builds in front of people to test them.

I wrote down what I learned as five principles that every screen has to pass:

1. **People before properties.** Show the person behind a listing before its specs and price. Renting is a trust decision first.
2. **Friction is a landlord problem too.** A hard listing flow means fewer good listings for everyone.
3. **The social layer is a feature.** Finding a flatmate is its own surface, not a tab inside the tenant dashboard.
4. **Right to left is not an afterthought.** Every design is checked in both directions before it ships.
5. **Mobile first means mobile native.** Browsing, messaging, and requests are built for a thumb on a small screen.

#### Physical data model

Every weight and tolerance sits in one config file. The SQL pre-ordering and the PHP scorer both read it, so a weight exists in exactly one place:

```php
'listing' => [
    'groups' => [
        'host_fit' => 35,    // does the person fit what the listing asks for?
        'seeker_fit' => 45,  // does the listing fit what the person asked for?
        'lifestyle' => 20,   // only for shared homes
    ],
    // ...factors: gender, age, smoking, pets, budget, city, move_in, area...
],
'dealbreakers' => [
    'gender' => 0.50,
    'smoking' => 0.70,
    'pets' => 0.80,
],
'tolerance' => [
    'budget_stretch' => 0.25,  // 25% over budget scores zero
    'move_in_days' => 45,
    'age_years' => 10,
],
```

#### Deep dive: the compatibility score

<MatchRanking />

The scorer is pure: it takes loaded models and runs no queries, which is what lets each row in a list call it without extra database work, and what lets the unit tests cover the real logic without a database.

Each factor returns a value between 0 and 1, or nothing when either side left it blank. Budget, for example, is a clean 1 under budget, because cheaper than asked is not a mismatch, and falls to zero at 25% over. The fold that turns factors into a score:

```php
foreach ($applicable as $group => $groupWeight) {
    $share = $groupWeight / $groupTotal;

    if (($total[$group] ?? 0) > 0) {
        $confidence += $share * (($seen[$group] ?? 0) / $total[$group]);
    }

    if (($seen[$group] ?? 0) > 0) {
        $scoreNum += $groupWeight * ($sum[$group] / $seen[$group]);
        $scoreDen += $groupWeight;
    }
}

$score = ($scoreNum / $scoreDen) * $this->dealbreakerDampener($values);
```

Within a group, the mean is taken only over factors that had data (`$seen`), and a group with no data drops out of the denominator. Confidence is the share of each group's weight that was actually evaluated. A dealbreaker dampens only when it was answered and failed: nobody is punished for a question the other side left blank. Roommate scoring is tested for symmetry, so two people always see the same score for each other.

#### Deep dive: making it fast

Performance went through three measured rounds, each written up with what was slow, what changed, and what was tried and reverted.

| Round | What was slow | What changed |
| --- | --- | --- |
| 1. The API | Production ran PHP's development server: one request at a time, with OPcache off, so Laravel recompiled on every request. 31 of 34 pages were client rendered, and the app layouts showed a blank screen until the session loaded. | FrankenPHP with OPcache and framework caches built at boot; skeleton layouts; composite indexes for the list queries. Public assets went from 30 MB to 7.0 MB. |
| 2. The landing page | Time to first byte 2.551 s, largest paint 5.463 s, 4 MB over 88 requests. The hero video downloaded inside the largest-paint window, and the frontend was served from the US to an audience in Morocco. | Locale routes prerendered; Vercel region moved from Washington to Paris; hero video deferred until after load; 67 KB of signed-in-only CSS split out. | 3. Two decisions went the other way on evidence. The React Compiler grew the client bundle from 744 KB to 843 KB gzipped, and this app's bottleneck is loading, not re-rendering, so I turned it off. #### Testing and delivery

The backend has 256 tests across 39 files: authentication, Google sign-in, email verification, matching and ranking, the gender rule, browse filters, requests and their cancellation, bookings, reports, notifications, and the admin console. The frontend has none, and nothing runs them automatically yet.

### Retrospective

Matching taught me to separate what the data says from what it does not. The first version treated a blank answer as a bad one, and a half-filled profile looked like a poor fit to everyone. Reporting confidence next to the score made the numbers honest, and made the empty fields worth filling.

Performance taught me to measure before deciding. Two of my first instincts, the React Compiler and skipping Redis, were wrong in opposite directions, and only the numbers said so.
